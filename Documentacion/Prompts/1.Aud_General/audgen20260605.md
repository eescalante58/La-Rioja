## **1\. Fallo de transaccionalidad en la creación de usuarios (Bug oculto / Riesgos técnicos)**

**Clasificación:** Crítico

* **Descripción:** En src/app/admin/settings/users/actions.ts, la función createNewUserInternal crea un usuario en Supabase Auth y posteriormente inserta el perfil en public.users. Supabase (PostgreSQL) no agrupa estas llamadas de API en una sola transacción.  
* **Impacto:** Si la creación en auth es exitosa pero la inserción en public.users falla, el sistema queda con un "usuario fantasma" que puede intentar loguearse pero no tiene rol, provocando caídas en la aplicación o inconsistencia de datos grave.  
* **Solución recomendada:** Implementar un mecanismo de compensación (rollback manual) eliminando al usuario de auth si la creación del perfil falla, o delegar la creación del perfil a un *Database Trigger* en Supabase.

**Ejemplo de código mejorado:**

`// 1. Create user in Supabase Auth`  
`const { data: authUser, error: authError } = await supabaseAdmin.auth.admin.createUser({...});`  
`if (authError) return { error: authError.message };`

`// 2. Profile update (public.users)`  
`const { error: profileError } = await supabaseAdmin.from("users").update({...}).eq("id", authUser.user.id);`

`if (profileError) {`  
  `// Rollback / Compensating Transaction`  
  `await supabaseAdmin.auth.admin.deleteUser(authUser.user.id);`  
  `console.error("Rollback ejecutado por fallo en perfil:", profileError);`  
  `return { error: "No se pudo completar el registro del usuario." };`  
`}`

## **2\. Violación del Principio de Responsabilidad Única (SRP \- SOLID) / Problemas de Mantenibilidad**

**Clasificación:** Alto

* **Descripción:** La Server Action submitContactForm en src/app/actions/contact.ts tiene múltiples responsabilidades: valida la entrada con Zod, resuelve configuraciones de entorno, mapea una allowlist de seguridad, persiste datos en Supabase e interactúa con un servicio externo (Resend) definiendo el template HTML del correo *inline*.  
* **Impacto:** Alta fragilidad. Si se decide cambiar el proveedor de correo, se debe alterar el controlador principal.  
* **Solución recomendada:** Adoptar un patrón de arquitectura en capas o puertos/adaptadores. Extraer el envío de correo y la persistencia a servicios dedicados (EmailService, ContactRepository).

**Ejemplo de código mejorado:**

`// En src/services/EmailService.ts`  
`export class EmailService {`  
  `static async sendContactAlert(data: SanitizedContactData, to: string) {`  
    `const htmlTemplate = ContactEmailTemplate(data); // Extraído a un componente`  
    `return await resend.emails.send({ to, subject: "Nueva Consulta", html: htmlTemplate });`  
  `}`  
`}`

`// En contact.ts (Server Action)`  
`export async function submitContactForm(rawInput: ContactInput) {`  
   `const data = validateContactInput(rawInput);`  
   `await ContactRepository.save(data);`  
   `await EmailService.sendContactAlert(data, resolvedEmail);`  
   `return { success: true };`  
`}`

## **3\. Componentes de UI monolíticos y Complejidad innecesaria**

**Clasificación:** Alto

* **Descripción:** El archivo src/app/about/page.tsx es masivo. Combina fetching de datos desde el CMS, lógica condicional, estilos y el marcado completo de múltiples secciones.  
* **Impacto:** La legibilidad está severamente comprometida y aumenta la carga cognitiva.  
* **Solución recomendada:** Refactorizar extrayendo cada sección (\<AboutHero /\>, \<MissionVision /\>) en sus propios archivos.

`// src/app/about/page.tsx`  
`export default async function AboutPage() {`  
  `const content = await getPageContent("about");`

`}`

## **5\. Código duplicado y Cross-Cutting Concerns dispersos**

**Clasificación:** Bajo

* **Descripción:** La función logActivity se invoca manualmente al final de cada operación de mutación.  
* **Impacto:** Código verboso ("Boilerplate").  
* **Solución recomendada:** Utilizar el patrón *Decorator* o integrarlo en la abstracción withRole/middlewares.

## **Recomendaciones Priorizadas**

1. **Corto Plazo (Sprint actual):** Implementar transacciones o fallbacks manuales (rollback) en la creación/actualización dual de usuarios en Supabase Auth y public schema.  
2. **Corto Plazo:** Eliminar tipados any en las Server Actions.  
3. **Mediano Plazo:** Refactorizar las grandes páginas públicas dividiéndolas en componentes de presentación más pequeños.  
4. **Largo Plazo:** Extraer la lógica de negocio hacia una capa de Servicios.
