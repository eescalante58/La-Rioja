# **Informe de Seguridad (OWASP Top 10) - Análisis Estático y Arquitectónico**

**Proyecto:** La-Rioja

**Fecha de Evaluación:** 5 de Junio de 2026

**Auditor:** Security Engineer (Especialista OWASP)

## **Resumen de Análisis por Categoría**

Se ha revisado el código en busca de las siguientes vulnerabilidades críticas:

* **Inyección SQL:** Mitigado en su mayoría por el uso del ORM/SDK de Supabase. No se detectaron consultas crudas.
* **XSS:** Mitigado en formularios (uso de escapeHTML y <SafeText>), pero existe riesgo residual en la subida de archivos (ver Vuln 1).
* **CSRF:** Mitigado por la protección nativa de *Server Actions* de Next.js (Origin/Host matching).
* **SSRF:** Mitigado. El envío de correos utiliza una lista blanca estricta (EMAIL\_ALLOWLIST) del lado del servidor.
* **Exposición de secretos:** Corregido en código (ya no se usa NEXT\_PUBLIC\_ para Service Role), pero requiere rotación obligatoria (ver Checklist).
* **Manejo inseguro de sesiones:** Mitigado en selectCompany mediante cookies httpOnly, secure y sameSite: "lax".

A continuación, se detallan los hallazgos activos que requieren intervención:

## **1. Validación Insuficiente (Subida Arbitraria de Archivos)**

* **Nivel de riesgo:** Alto
* **Categoría OWASP:** A04:2021-Insecure Design / A08:2021-Software and Data Integrity Failures
* **Evidencia encontrada:** En src/app/admin/settings/users/actions.ts, la función uploadUserAvatar(file: FormData) extrae el archivo y lo sube directamente a Supabase Storage: supabase.storage.from("user\_avatar").upload(fileName, image). No hay validación de tipo MIME, extensión o tamaño en el backend.
* **Escenario de ataque:** Un atacante autenticado intercepta la petición y sube un archivo masivo (causando Denegación de Servicio o agotando la cuota de almacenamiento) o sube un archivo malicioso (ej. avatar.svg con un payload JavaScript incrustado). Al ser servido desde el storage público, ejecutará un **Stored XSS** en el navegador de cualquier administrador que visualice dicho perfil.
* **Recomendación:** Implementar validación estricta del tamaño del archivo y de los tipos MIME permitidos (imágenes estándar).
* **Ejemplo de mitigación:**

export async function uploadUserAvatar(file: FormData) {  
const image = file.get("avatar") as File;

// 1. Validar tamaño (ej. máximo 2MB)  
if (image.size > 2 \* 1024 \* 1024) throw new Error("El archivo excede el límite de 2MB.");

// 2. Validar tipo MIME  
const allowedTypes = \["image/jpeg", "image/png", "image/webp"];  
if (!allowedTypes.includes(image.type)) throw new Error("Formato de imagen no permitido.");

// ... lógica de subida ...  
}

## **2. Control de Acceso Débil (IDOR - Insecure Direct Object Reference)**

* **Nivel de riesgo:** Alto
* **Categoría OWASP:** A01:2021-Broken Access Control
* **Evidencia encontrada:** En src/app/admin/settings/users/actions.ts, la Server Action getUserCompanies(userId: string) acepta un userId pero no verifica si quien llama a la función es el dueño de ese ID o un administrador autorizado.
* **Escenario de ataque:** Un usuario con rol de solo lectura puede invocar esta acción directamente desde la consola del navegador pasando el UUID de un superadministrador. Esto filtraría información confidencial sobre la topología empresarial de la plataforma.
* **Recomendación:** Aplicar validación de control de acceso basada en la identidad del usuario que realiza la petición y su nivel de privilegios.
* **Ejemplo de mitigación:**

export async function getUserCompanies(targetUserId: string) {  
const supabase = await createClient();  
const { data: { user } } = await supabase.auth.getUser();  
if (!user) return \[];

const { level } = await requireRoleLevel(0);

// Bloquear si el usuario intenta ver datos ajenos sin ser Administrador (nivel >= 80)  
if (user.id !== targetUserId \&\& level < 80) {  
throw new Error("No tienes permisos para ver las empresas de este usuario.");  
}

// ... lógica de consulta a Supabase ...  
}

## **3. Manejo Inseguro de Identificadores (Path Traversal en Storage)**

* **Nivel de riesgo:** Medio
* **Categoría OWASP:** A01:2021-Broken Access Control
* **Evidencia encontrada:** En uploadUserAvatar, la construcción del nombre del archivo es: const fileName = \\${Date.now()}-${image.name}`;`.
* **Escenario de ataque:** El valor image.name está bajo el control absoluto del cliente. Un atacante puede manipular la petición HTTP para enviar un nombre como ../../../bucket\_root/overwrite\_file.jpg. Confiar en rutas proporcionadas por el cliente abre la puerta a la manipulación de directorios o evasión de filtros.
* **Recomendación:** Descartar el nombre original del archivo por completo. Utilizar identificadores generados criptográficamente por el servidor (UUIDs) y agregar solo la extensión sanitizada.
* **Ejemplo de mitigación:**

  import { extname } from "path";  
// Generar nombre seguro: UUID + extensión extraída del tipo MIME o archivo original (sanitizada)  
const extension = image.name.split('.').pop()?.replace(/\[^a-z0-9]/gi, '');  
const safeFileName = `${crypto.randomUUID()}.${extension}`;

  ## **4. Validación de Entrada Deficiente (Falta de Rate Limiting y DoS)**

* **Nivel de riesgo:** Medio
* **Categoría OWASP:** A05:2021-Security Misconfiguration / A07:2021-Identification and Authentication Failures
* **Evidencia encontrada:** 1. No hay límites en la recuperación de contraseñas ni en el envío de mensajes de contacto (submitContactForm).  
2. Consultas a bases de datos como getUsersWithRoles() no utilizan paginación (.limit()).
* **Escenario de ataque:** - Un bot puede enviar 10,000 peticiones al formulario de contacto, agotando la cuota mensual de la API de Resend (Denial of Wallet).

  * Un ataque automatizado que genere miles de usuarios provocará que getUsersWithRoles() consuma toda la memoria del servidor Node.js (Next.js) al intentar procesar un payload masivo.
* **Recomendación:** Implementar un mecanismo de *Rate Limiting* por IP y forzar la paginación a nivel de base de datos.
* **Ejemplo de mitigación (Paginación en Supabase):**

  export async function getUsersWithRoles(page = 0, pageSize = 50) {  
// ...  
const { data, error } = await supabase  
.from("users")  
.select("\*, roles:role\_id (name, level)")  
.range(page \* pageSize, (page + 1) \* pageSize - 1)  
.order("full\_name", { ascending: true });  
}

  ## **5. Acciones Obligatorias Antes de Producción (Go-Live Checklist)**

  El proyecto **no debe pasar a producción** sin completar y firmar los siguientes puntos:

* \[ ] **1. Rotación de Secretos (Crítico):** Debido al uso histórico de NEXT\_PUBLIC\_SUPABASE\_SERVICE\_ROLE\_KEY (expuesto al cliente), es obligatorio ir al dashboard de Supabase, **invalidar** el Service Role Secret actual y generar uno nuevo. Actualizar los archivos .env.production.
* \[ ] **2. Sanitización de Storage:** Aplicar la mitigación de Vuln 1 y Vuln 3 en todas las funciones que guarden archivos (CMS, avatares, facturas del módulo Bingo).
* \[ ] **3. Cierre de Brechas IDOR:** Revisar la totalidad de las *Server Actions* (updateUser, getUserCompanies, mutaciones de CMS) asegurando que existe el guard: if (user.id !== targetId \&\& !isAdmin) throw Error().
* \[ ] **4. Rate Limiting en APIs Públicas:** Integrar @upstash/ratelimit o una solución equivalente en el middleware de Next.js para proteger las rutas /api/auth/ y la Server Action submitContactForm (ej. max 5 peticiones por minuto por IP).
* \[ ] **5. Restricción de Origen (CORS y CSP):** Configurar remotePatterns en next.config.mjs para asegurar que el componente <Image> de Next.js solo cargue imágenes desde dominios controlados (Supabase Storage) y evitar ataques SSRF.
